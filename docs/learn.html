    Graphene v0.3

    Learn Graphene in 14 short lessons

    Graphene (.grph) is a small language for business logic. A program is a graph of values and effects, and the compiler proves it safe before anything runs: every input ends in exactly one result, every failure is handled, and running in parallel gives exactly the same answer as running in order.

    Each lesson takes a few minutes. Every program on this page passes graphene check, and every output shown is what graphene run really prints.

    1

    Your first program

    Write, check and run a program that doubles a number.

    #!graphene 0.3
@intent "Double a number"

in x: u64 -> X
X -> f(x * 2) -> Y
Y -> out result: u64

assert total
    • #!graphene 0.3 is required on the first line. It says which version of the language the file uses.
    • @intent is a one-line description for humans (and the IDE).
    • in x: u64 -> X declares an input named x of type u64, and a node X where the flow starts.
    • X -> f(x * 2) -> Y is a flow: when X is ready, compute x * 2 and store it in node Y.
    • out result: u64 is the program's result. assert total asks the compiler to prove every input reaches exactly one result.

    Try it

    graphene check hello.grph
graphene run hello.grph --arg x=21
    ok: hello.grph (2 values, 2 operations)
{ "result": { "ok": { "result": 42 } }, "effects": [] }
    Naming rule of thumb: lowercase names are inputs (values you read in expressions), UPPERCASE names are nodes in the graph.
    Check yourself: what does --arg x=21 refer to, x or X?

    The input's name, x. X is the node where the flow starts; you never pass values to nodes directly.

    2

    Flows, branches and joins

    Split work into branches that run independently, then join them.

    #!graphene 0.3
@intent "Price with tax and a delivery fee"

in price: dec -> P
P -> f(price * 0.21) -> TAX
P -> f(price + 4.99) -> WITH_FEE
(TAX, WITH_FEE) -> f(WITH_FEE + TAX) -> TOTAL
TOTAL -> out total: dec

assert total
    • Two flows leave P. They don't depend on each other, so the runtime may compute them in parallel.
    • (TAX, WITH_FEE) -> f(...) is a join: it waits until both are ready.
    • An expression can read any node that is guaranteed to have run before it, like TAX and WITH_FEE here.
    graphene run total.grph --arg price=10.00
graphene run total.grph --arg price=10.00 --parallel
    { "result": { "ok": { "total": "17.09" } }, "effects": [] }

    10.00 × 0.21 = 2.10, and 10.00 + 4.99 = 14.99, so the total is 17.09. Both commands print exactly the same thing: that's a guarantee, not luck.

    Check yourself: why is dec output a string like "17.09"?

    dec is an exact decimal (never floating point). Writing it as a string keeps every digit exact in JSON. Results are shown with 2 decimal places unless you ask for another scale (lesson 9).

    Types and records

    Know the five scalar types, build records, and convert between numbers.

    TypeValuesLiteral
    u64whole numbers ≥ 042
    i64whole numbers, may be negative42 (from context)
    decexact decimals0.80 (always with a point)
    booltrue / falsetrue
    strtext"hello"
    {a: T, ...}records{qty: 2, amount: 7.50}

    Numbers never mix silently. This is an error:

    Q -> f(qty * unit) -> AMOUNT   // qty: u64, unit: dec
    G003  × cannot apply `*` to `u64` and `dec`
  help: Graphene has no implicit conversions: make both sides the same type

    Convert explicitly with u64(e), i64(e) or dec(e), and group values in a record:

    #!graphene 0.3
@intent "One order line as a record"

in qty: u64 -> Q
in unit: dec
Q -> f({qty: qty, amount: dec(qty) * unit}) -> LINE
LINE -> out line: {qty: u64, amount: dec}

assert total
    { "result": { "ok": { "line": { "amount": "7.50", "qty": 3 } } }, "effects": [] }
    Notice in unit: dec has no node. An input without -> Node is just a value you can read anywhere.
    Check yourself: how do you read the amount field of node LINE?

    LINE.amount.

    4

    Decisions with match

    Branch on a value, and bring the branches back together.

    #!graphene 0.3
@intent "Grade an exam"

in score: u64 -> S
S -> match score >= 50 { true => PASSED, false => FAILED }
PASSED -> f("pass") -> GRADE
FAILED -> f("fail") -> GRADE
GRADE -> out grade: str

assert total
    • Exactly one arm runs. The other branch is inactive and does nothing.
    • Two flows write GRADE. That's a merge, allowed because the writers can never both run.
    • You can match on bool, str, u64 and i64. Use _ => for "anything else".
    { "result": { "ok": { "grade": "pass" } }, "effects": [] }

    Every match must cover every possible value:

    L -> match level { "gold" => G, "silver" => S }
    G004  × match on `str` is not exhaustive
  help: add a wildcard arm: `_ => Node`
    Check yourself: fix the mistake above so bronze and everyone else pay full price.

    L -> match level { "gold" => G, "silver" => S, _ => OTHER }, then OTHER -> f(1.00) -> RATE.

    5

    Effects and their errors

    Call the outside world, and handle every way it can fail.

    #!graphene 0.3
@intent "Greet a user by name"

extern fx GetUser(id: u64) -> {name: str, vip: bool} ! NotFound | DbDown

in id: u64 -> I
I -> fx GetUser(id: id) -> U | err NotFound -> GUEST | err DbDown -> DOWN
U -> f(U.name) -> NAME
GUEST -> f("guest") -> NAME
DOWN -> fail
NAME -> out name: str

assert total
    • extern fx declares an effect: its arguments, its result type, and after ! the errors it can return.
    • fx GetUser(...) calls it. | err NotFound -> GUEST routes that error to its own node. Every declared error must be handled (G005), or caught all at once with | err -> X.
    • Here a missing user recovers as "guest", while a database outage fails (lesson 7).

    To run it without a real database, give fake answers in a mock fixture:

    {
  "effects": {
    "GetUser": {
      "cases": [
        { "args": { "id": 1 }, "ok": { "name": "ana", "vip": true } },
        { "args": { "id": 9 }, "err": "DbDown" }
      ],
      "fallback": { "err": "NotFound" }
    }
  }
}
    graphene run greet.grph --arg id=1 --mock users.json   # ana
graphene run greet.grph --arg id=5 --mock users.json   # guest
graphene run greet.grph --arg id=9 --mock users.json   # fails with DbDown
    {
  "result": { "ok": { "name": "ana" } },
  "effects": [
    { "kind": "fx", "effect": "GetUser", "args": { "id": 1 },
      "result": { "ok": { "name": "ana", "vip": true } } }
  ]
}

    The effect log lists every outside call, in a fixed order, with its arguments and answer. Without --mock, the run stops with fault[R003]: no mock response for `GetUser`.

    Check yourself: what does id=9 print as its result?

    {"err": "DbDown"}. A bare fail on an error node passes the effect's error through.

    6

    Fire and forget: fx~ and sinks

    Log, notify and audit without any risk of changing the result.

    extern fx~ Log(event: str)

NAME -> fx~ Log(event: "greeted " + NAME) -> sink LOGGED

assert indep(LOGGED, out)
    • extern fx~ declares a fire-and-forget effect: no result, no errors.
    • Its target is a sink: nothing may read it or continue from it (G010).
    • assert indep(LOGGED, out) asks the compiler to prove the log can never influence the result.
    • Fire-and-forget calls are delivered after the run finishes, and only if the run got that far.
    [
  { "kind": "fx",  "effect": "GetUser", "args": { "id": 1 }, "result": { "ok": { "name": "ana", "vip": true } } },
  { "kind": "fx~", "effect": "Log", "args": { "event": "greeted ana" } }
]
    Check yourself: when DbDown happens, is Log called?

    No. NAME never gets a value on that path, so everything after it stays inactive.

    7

    Failing on purpose

    End a run with a named error, and let the compiler find paths you forgot.

    #!graphene 0.3
@intent "Withdraw money if the balance allows it"

in balance: dec -> B
in amount: dec
B -> match balance >= amount { true => OK, false => TOO_LOW }
OK -> f(balance - amount) -> LEFT
TOO_LOW -> fail InsufficientFunds
LEFT -> out left: dec

assert total
    { "result": { "err": "InsufficientFunds" }, "effects": [] }
    • fail Name ends the run with that error. It's a normal ending (exit code 0), not a crash.
    • Every run reaches exactly one out or fail.

    Delete the TOO_LOW -> fail ... line and the compiler notices at once:

    G008  × `TOO_LOW` never reaches an `out`, `fail`, or sink
  help: use this value on the way to a result, or remove the statement that produces it
    Stuck on a code? graphene explain G008 prints what it means and how to fix it.
    8

    The safety rules

    Understand the three flow rules the compiler enforces, so its errors make sense.

    RuleMeaningCode
    Merges are exclusiveSeveral flows may write one node only if they can never both run (different arms of one decision).G006
    Joins are togetherA join waits for all its members, so they must be active together. In 0.3, a member whose condition implies the others' is fine.G007
    Read what surely ranAn expression may only read a node that is guaranteed to have run before it.G009
    X -> f(x + 1) -> Y
X -> f(x + 2) -> Y
    G006  × merge `Y` has writers that can both run

    These rules are why parallel and sequential runs always agree: no node can be written twice, and nothing waits for a value that might never come.

    Check yourself: why was the merge in lesson 4 allowed?

    Its writers were the true and false arms of the same match, so exactly one of them runs.

    9

    Constants, rounding and text

    Name your policy numbers, round on purpose, and build messages.

    #!graphene 0.3
@intent "Split a restaurant bill"

const SERVICE: dec = 0.125
const VAT: dec = 0.21

in amount: dec -> A
in guest: str
A -> f({
  service: round(amount * SERVICE, 2),
  vat: ceil(amount * VAT, 1),
  total: round(amount * (1.00 + SERVICE + VAT), 2),
  note: "thanks, " + guest,
}) -> BILL
BILL -> out bill: {service: dec, vat: dec(1), total: dec, note: str}

assert total
    • const names a value used anywhere, including inside subgraphs. An unused constant is G008.
    • round, floor and ceil take the number of decimal places.
    • dec(1) in a type shows that output with 1 decimal place instead of 2.
    • + joins two strings. Long statements may span lines inside brackets.
    { "result": { "ok": { "bill": {
  "note": "thanks, ana", "service": "5.00", "total": "53.40", "vat": "8.4" } } }, "effects": [] }

    Lists

    Take a list as input and summarize it with built-in functions.

    #!graphene 0.3
@intent "Summarize exam scores"

in scores: [u64] -> S
S -> f({
  count: len(scores),
  best: max(scores),
  total: sum(scores),
  has_perfect: contains(scores, 100),
}) -> SUMMARY
SUMMARY -> out summary: {count: u64, best: u64, total: u64, has_perfect: bool}

assert total
    { "result": { "ok": { "summary": {
  "best": 100, "count": 3, "has_perfect": true, "total": 220 } } }, "effects": [] }
    WriteGives
    [1, 2, 3], []a list literal (an empty one needs a known type)
    LINES.amountthe amount of every record in the list
    len, sum, min, maxcount, total, smallest, largest
    all, anyfor lists of bool
    contains(xs, v)is v in the list?
    max and min of an empty list stop the run with R006. Try --arg 'scores=[]'. Check len(xs) > 0 with a match first when a list may be empty.

    Subgraphs: reusable pieces

    Write a rule once, check it once, and call it wherever you need it.

    #!graphene 0.3
@intent "Apply one discount rule to two prices"

graph Discount(price: dec -> P, vip: bool) -> dec {
  P -> match vip { true => YES, false => NO }
  YES -> f(round(price * 0.90, 2)) -> R
  NO -> f(price) -> R
  R -> out
}

in a: dec -> A
in b: dec
in vip: bool
A -> call Discount(price: a, vip: vip) -> DA
DA -> call Discount(price: b, vip: vip) -> DB
DB -> f(DA + DB) -> TOTAL
TOTAL -> out total: dec

assert total
    • graph Name(params) -> Type { ... } declares a subgraph. Its parameters work like inputs; its body ends in a bare out.
    • A subgraph that can fail lists its errors: -> dec ! Banned. Callers handle them with | err ..., exactly as with effects.
    • Each body is checked on its own, and must always be total. Subgraphs can call other subgraphs, but never themselves (G015).
    { "result": { "ok": { "total": "14.00" } }, "effects": [] }

    10.00 × 0.90 = 9.00, and 5.55 × 0.90 = 4.995, which rounds to 5.00.

    map, filter and each

    Run a subgraph or an effect once per list element.

    #!graphene 0.3
@intent "Price every cart line and count the big ones"

extern fx~ Notify(amount: dec)

graph LineTotal(line: {qty: u64, price: dec} -> L) -> dec {
  L -> f(dec(line.qty) * line.price) -> T
  T -> out
}

graph IsBig(amount: dec -> A) -> bool {
  A -> f(amount > 100.00) -> B
  B -> out
}

in cart: [{qty: u64, price: dec}] -> C
C -> map LineTotal(line: each cart) -> TOTALS
TOTALS -> filter IsBig(amount: each TOTALS) -> BIG
BIG -> fx~ Notify(amount: each BIG) -> sink TOLD
BIG -> f({sum: sum(TOTALS), big_lines: len(BIG)}) -> R
R -> out result: {sum: dec, big_lines: u64}

assert total
assert indep(TOLD, out)
    • map runs the subgraph once per element and gives a list of results, in order. Elements may run in parallel.
    • filter keeps the elements whose subgraph returns true.
    • each marks the one argument that is the list. Other arguments are passed to every element unchanged.
    • each also works on effects: Notify is sent once per big line.
    • If several elements fail, every element still runs and the first one in the list decides the error, so results never depend on timing.
    graphene run cart.grph --arg 'cart=[{"qty":2,"price":"30.00"},{"qty":1,"price":"150.00"},{"qty":5,"price":"25.00"}]'
    {
  "result": { "ok": { "result": { "big_lines": 2, "sum": "335.00" } } },
  "effects": [
    { "kind": "fx~", "effect": "Notify", "args": { "amount": "150.00" }, "at": [["Notify", 0]] },
    { "kind": "fx~", "effect": "Notify", "args": { "amount": "125.00" }, "at": [["Notify", 1]] }
  ]
}

    The lines total 60.00, 150.00 and 125.00. The "at" path says which element each log entry came from.

    Check yourself: what happens with map LineTotal(line: cart), without each?

    G016: a map needs exactly one argument marked each, and it must be a list of the parameter's type.

    14

    Real effects, recording, and the IDE

    Answer effects for real, turn real runs into tests, and work visually.

    Mocks are for tests. A host config sends each effect to an HTTP endpoint or a local command instead:

    {
  "effects": {
    "GetUser": { "http": "https://api.example.com/users", "timeout_ms": 2000,
                 "headers": { "Authorization": "env:USERS_TOKEN" } },
    "Charge":  { "command": ["python", "scripts/charge.py"] }
  },
  "default": "mock:users.json"
}
    graphene run greet.grph --arg id=1 --host hosts.json --record replay.json
graphene run greet.grph --arg id=1 --mock replay.json     # the same run, offline
    • Hosts receive {"effect": ..., "args": {...}} and answer {"ok": value} or {"err": "Variant"}.
    • env:NAME reads secrets from the environment, so they never sit in the file.
    • A timeout or broken connection is R007: a problem with the environment, not your program.
    • --record saves every answer as a mock, so a real run becomes a repeatable test.
    Graphene IDE shows the same program as text and as a live graph. Edit either one, run with mocks or real hosts, step through a run, open subgraphs, and see untested branches dashed on the graph.
