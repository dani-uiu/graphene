# Graphene v0.3 — proposal

Status: **implemented** in v0.3.0 (decisions in §13). Deferred: the IDE's "extract selection into a subgraph" command; add a subgraph and a `call` step instead.

After approval, these rules move into `grammar.ebnf`, `semantics.md` (§7) and `decisions.md` (D-043 onward).

## Goal

Writing `marketplace_checkout.grph` hit three walls:

1. **A checkout can hold only one item.** There are no lists, so there is no way to price or reserve "each line" of a cart.
2. **Parallel branches can't both be able to fail.** A branch that can fail can't be joined with one that can't (G007), so tax and shipping only ran in parallel because both recovered from their errors.
3. **No reuse.** The logic for one line or one payment attempt can't be named and called twice.

v0.3 removes all three, and adds what it takes to run programs against **real services** instead of only mocks. As before, every v0.2 program stays valid and behaves the same.

| # | Change | Kind |
|---|---|---|
| 1 | **Subgraphs**: named, checked sub-programs, called with `call` | language |
| 2 | **Lists** `[T]`, list literals, field projection, built-in aggregates | language |
| 3 | **`map` and `filter`**: run a subgraph on every element, in parallel | language |
| 4 | **Relaxed joins** and **references to guaranteed values** | checker |
| 5 | **Rounding** `round/floor/ceil`, output scale `dec(N)`, string `+` | language |
| 6 | **Real effect hosts** (process and HTTP), with **record and replay** | runtime |
| 7 | **IDE support** for subgraphs, lists, and real hosts | tooling |
| 8 | **`each` on effects**: call an effect once per list element without writing a subgraph | language |
| 9 | **Statements over several lines** inside brackets, and a formatter that wraps long lines | syntax |
| 10 | **Named constants** (`const RISK_LIMIT: u64 = 80`) | language |
| 11 | **"Did you mean…?" hints**, and runtime faults that show the offending values | diagnostics |
| 12 | **Outcome coverage**: `graphene test --coverage` lists the outcomes and branches no case reaches | tooling |
| 13 | **CI and release builds**: GitHub Actions runs every check and builds the IDE installers | project |

---

## 0. Versioning

`#!graphene 0.3` is added. P006 is generalized to "`<feature>` requires `#!graphene 0.3`". A 0.1 or 0.2 file means exactly what it meant before (D-036).

## 1. Subgraphs and `call`

A **subgraph** is a named program inside a file. It has typed parameters, one result type, and the errors it can fail with.

```
graph PriceLine(line: {sku: str, qty: u64} -> L) -> {sku: str, amount: dec} ! UnknownSku {
  L -> fx Catalog(sku: line.sku) -> ITEM | err -> MISSING
  MISSING -> fail
  ITEM -> f({sku: line.sku, amount: ITEM.price * dec(line.qty)}) -> LINE
  LINE -> out
}
```

**Declaration**
- The block starts with `graph Name(params) -> Type ! Errors {` on its own line and ends with `}` on its own line.
- Parameters use the same form as `in`: `name: T`, with an optional `-> Node`.
- The body is ordinary Graphene. It ends in exactly one `out` (bare, with no name, because the type comes from the header) and any number of `fail`s.
- Subgraphs may not be nested. All `extern`s are declared at the top level and shared.

**Calling it**
```
X -> call PriceLine(line: ORD.line) -> PRICED | err UnknownSku -> MISSING
```
- A call has the same shape as an `fx` call: named arguments, a result node, and error edges routed by variant (D-031 rules: coverage is G005, unknown variants G002, redundancy G014).

**Checks**
- **Checked once, on its own.** The body must be total (G020 applies inside every subgraph, whether or not it says `assert total`). It may have its own `assert indep`.
- **Signature:** the `out` value must have the declared result type (G003). Every error that can reach a `fail` must be declared: either a named `fail Name`, or a variant propagated by a bare `fail`. A missing one is the new **G017**.
- **No recursion:** the call graph between subgraphs must be acyclic. A cycle is the new **G015**, which keeps every program terminating and checkable.

**Runtime**
- A call runs the body as a nested run.
- Effects inside the body appear in the caller's log, in order. Each entry gets an `"at"` path such as `"PriceLine"`, or `"PriceLine[2]"` inside a map.

## 2. Lists

| Form | Meaning |
|---|---|
| `[T]` | type: a list of `T` (any type, including records and lists) |
| `[a, b, c]` | literal: elements must share one type. `[]` needs an expected type, from an annotation or a parameter (G003 otherwise). |
| `xs.field` | **projection**: on a list of records, the list of that field, e.g. `LINES.amount : [dec]` |
| `len(xs)` | `u64` |
| `sum(xs)` | numeric list, gives its element type. The sum of an empty list is `0` (`0.00` for `dec`). |
| `min(xs)`, `max(xs)` | numeric or `str` list. An empty list is the new runtime fault **R006**. |
| `all(xs)`, `any(xs)` | `[bool]` gives `bool`. `all([])` is true, `any([])` is false. |
| `contains(xs, v)` | `bool`. `v` must have the element type. |

- **Inputs** may be lists of scalars or records. On the CLI they are written as JSON: `--arg 'cart=[{"sku":"mug","qty":2}]'`. This is a deliberate exception to D-014's "scalar inputs only".
- **No indexing (`xs[i]`).** Every list operation above is total or has a clear fault, and indexing would invite off-by-one faults. Use `filter` with a subgraph instead.
- The built-in names stay ordinary identifiers, because `IDENT "("` only ever means a call.

## 3. `map` and `filter`

```
C -> map PriceLine(line: each cart) -> LINES | err -> BAD_LINE
LINES -> filter IsHeavy(line: each LINES) -> HEAVY
```

- **`each`:** exactly one argument is marked `each`, and it must be a list `[T]` where the parameter has type `T`. The other arguments are passed unchanged to every element. No `each`, more than one, or a non-list is the new **G016**.
- **`map`** returns `[R]`, the subgraph's result for every element, in input order.
- **`filter`** needs a subgraph that returns `bool`, and returns the elements, in order, for which it returned `true`.

**Failure policy (D-045)**
- **Every element runs, even if one fails.** That matches D-015 (no early termination) and keeps logs identical between sequential and parallel runs.
- If any element fails, the map takes the error edge with the error of the **lowest-index** failing element. That is deterministic.
- Error edges are checked against the subgraph's declared errors, exactly like `call`.

**Parallelism**
- Elements run in parallel, and effects in different elements may overlap.
- The log is ordered by the map op's position, then the element index, then the position inside the body. The order never depends on timing.
- The 200× parallel-versus-sequential test covers maps.

**Guards:** a map with error edges is a decision with outcomes `ok` and each error edge, exactly like `fx`. Totality and merge checks need no new rules.

## 4. Relaxed joins and guaranteed references

Both use one new relation on guards: **implication**. `g1 ⇒ g2` holds when every minterm of `g1` contains some minterm of `g2`. It is checked structurally, so it stays sound and decidable.

**Relaxed G007 (D-046).** A join is allowed when its members' guards form a chain under implication: there is a most specific member `g*` that implies every other member's guard. The join is active exactly when `g*` is. That is one of the existing guards, so the guard invariant (decisions conjoin only onto their own guards) still holds. G007 now fires only for guards that can't be ordered this way, such as two different arms of the same match.

This makes the v0.2 example from `docs/v0.2.md` §8 legal:

```
STOCKED -> fx DbFetch(...) -> USR | err NotFound -> GUEST | err DbDown -> DOWN   // RATE: ok ∨ NotFound
STOCKED -> fx ShipQuote(...) -> SHIP | err -> NO_ROUTE                           // SHIP: always (under STOCKED)
(RATE, SHIP) -> f(...) -> BILL     // v0.2: G007.  v0.3: fine, active exactly when RATE is.
```

**Guaranteed references (D-047).** An expression in op `o` may reference value `X` when both of these hold:
- `X` is a **flow ancestor** of `o`, so `o` always runs after `X`, in both runners;
- `g(o) ⇒ g(X)`, so whenever `o` runs, `X` has a value.

Dominance (G009 today) is a special case of this. G009 now fires only when one of the two conditions fails, and the help line says which one.

## 5. Rounding, output scale, strings

| Form | Meaning |
|---|---|
| `round(x, n)` | `dec`, `n` a literal 0–28. Rounds half away from zero, like D-002. |
| `floor(x, n)`, `ceil(x, n)` | `dec`, rounding toward −∞ / +∞ |
| `dec(N)` in a type | Output scale. `out total: dec(4)` emits 4 places instead of 2. It is still type `dec` for every check; only the output rescaling changes. Allowed inside records and lists: `{total: dec(4)}`. |
| `a + b` on `str` | Concatenation, e.g. messages like `"order " + sku + " shipped"` |

There is still no `str` ↔ number conversion. Formatting numbers into strings needs a decision on locale and scale, so it is deferred.

## 6. Real effect hosts, record and replay

Today every effect is answered by a mock. v0.3 adds hosts that call real services, configured outside the program. The program itself never contains URLs, commands or secrets.

```
graphene run order.grph --arg order_id=1 --host hosts.json --record replay/order-1.json
graphene run order.grph --arg order_id=1 --mock replay/order-1.json        # identical run, offline
```

`hosts.json`:
```json
{
  "effects": {
    "Catalog": { "http": "https://api.example.com/catalog", "timeout_ms": 2000,
                 "headers": { "Authorization": "env:CATALOG_TOKEN" } },
    "Charge":  { "command": ["python", "scripts/charge.py"], "timeout_ms": 5000 },
    "Audit":   { "command": ["scripts/audit.sh"] }
  },
  "default": "mock:fixtures/dev.json"
}
```

**Protocol**
- A host receives `{"effect": "Catalog", "args": {...}}`, as an HTTP POST body or as one JSON line on stdin.
- It answers `{"ok": value}` or `{"err": "Variant"}`.
- Answers are type-checked against the `extern`, exactly like mocks (R004).

**Failures**
- A timeout, connection error or bad response is the new runtime fault **R007**. It is not a program error.
- Domain failures should be declared variants, so the program can handle them.

**Secrets:** header values like `env:NAME` are read from the environment, so secrets never live in the config file.

**`fx~` ordering (D-048).**
- Sync calls to a real host happen when the op runs. They can't be undone, so compensation is the program's job (see `Release` in the checkout examples).
- **Async `fx~` emits are buffered** and delivered at the end of the run, in log order, and only those positioned before a fault are delivered. This closes the gap noted in D-012: parallel mode can no longer send an async effect that the sequential run would not have sent.

**Record and replay**
- `--record file.json` writes every sync answer of a real run as a mock fixture, keyed by arguments.
- Replaying that fixture reproduces the run exactly, which makes debugging and test cases from production data easy.
- `graphene test` can point cases at recorded fixtures.

**No tokio (D-020 stands).** HTTP uses a blocking client (`ureq`), and process hosts use `std::process`. Each call runs on the worker thread already executing that op.

## 7. IDE

- **Subgraphs:**
  - each `graph` block appears as a collapsible group in the graph view;
  - double-clicking a `call`, `map` or `filter` node opens the subgraph's own graph, with a breadcrumb back to the caller.
- **Lists:**
  - nodes show `[n items]` and the first values;
  - map nodes show a `×n` badge;
  - after a run, an element picker shows the trace of any single element.
- **Hosts:**
  - the Run panel gets a host picker (mock, or a `hosts.json`);
  - a **Record** toggle writes the replay fixture;
  - one click turns a recorded run into a test case.
- **Edit commands:** add subgraph, extract selection into a subgraph (turns selected statements into a `graph` block plus a `call`), add `call` / `map` / `filter` step, add list input.

## 8. Smaller additions

These came from writing the v0.2 examples and the IDE. Each one is small, but they add up.

### 8.1 `each` on effects (D-049)

Calling one effect per list element shouldn't need a subgraph:

```
HELD -> fx~ Release(reservation: each HELD) -> sink GONE                         // one emit per element
SKUS -> fx Catalog(sku: each skus) -> ITEMS | err UnknownSku -> MISSING          // [ {price, kg} ]
```

- **Same rules as `map`.** Exactly one argument is marked `each` (G016). Every element runs, the lowest-index error wins, and log order is (op, element index).
- **Results:** an `fx` with `each` gives `[R]`. An `fx~` with `each` emits once per element and still flows into a sink.

### 8.2 Statements over several lines (D-050)

Today every statement must fit on one line. That gives lines over 200 characters in `marketplace_checkout.grph`, which are hard for people to read and for diffs to show.

**Rule:** a newline inside an open `(`, `{` or `[` doesn't end the statement. That is the only new rule.

```
(TAX_RATE, SHIPPING) -> f({
  subtotal: SUBTOTAL,
  tax: SUBTOTAL * TAX_RATE,
  shipping: SHIPPING,
  total: SUBTOTAL + SUBTOTAL * TAX_RATE + SHIPPING,
}) -> BILL
```

**Formatter:** `fmt` wraps any statement longer than 100 characters at the outermost record or argument list, one field per line, with a trailing comma, and joins short ones back onto one line. Comments inside a wrapped statement are kept.

**IDE:** the IDE's statement ids become "first line of the statement", and edit commands replace the whole statement span instead of one line.

### 8.3 Named constants (D-051)

```
const RISK_LIMIT: u64 = 80
const DEFAULT_TAX: dec = 0.10
BUY -> match BUY.risk > RISK_LIMIT { true => RISKY, false => TRUSTED }
```

- **What a constant is:** a typed literal, or a record or list of literals, declared at the top level. It can be used in any expression and inside subgraphs.
- **What it isn't:** a constant isn't a graph node, so it adds no vertices and no dependencies.
- **Checks:** redefining a constant is G013. A constant whose value doesn't match its type is G003. An unused constant is G008, to match unused inputs.
- **Why:** an LLM reading `RISK_LIMIT` understands the rule. Reading `80`, it has to guess.

### 8.4 Better messages (D-052)

- **Name typos:** G002 suggests the closest defined name of the right kind, e.g. "`ITM` is not defined here, did you mean `ITEM`?". The same applies to unknown fields, parameters, error variants and effects. Suggestions only appear when the edit distance is at most 2, so they're never wild guesses.
- **Faults show values:**
  - R001: "value -1 out of range for `u64`" and "`18446744073709551615 * 2` overflows `u64`";
  - R003 and R004: show the effect, the arguments, and the answer received.
- **`graphene explain G005`:** prints the code's meaning, a minimal failing program, and the fix. The text comes from the same table the README uses.

### 8.5 Outcome coverage (D-053)

`graphene test --coverage` runs every case and reports, per program:
- which **outcomes** (`out` and every `fail`) at least one case reached;
- which **decision outcomes** (match arms, error edges, map failures) were taken;
- which **effects** were called.

```
marketplace_checkout.grph   outcomes 11/11   branches 31/33   effects 11/11
  never taken: line 43 `RATE -> match coupon` arm "FREESHIP" with NO_ROUTE ...
```

- **Built on the existing guard model:** the checker already knows every outcome and branch, so coverage is just which of them the cases hit.
- **In the IDE:** branches no case reaches are drawn dashed, and the Tests panel shows the totals.
- **`--min-outcomes 100`:** makes the command fail when coverage is below the threshold, for use in CI.

### 8.6 CI and release builds (D-054)

- **Checks:** a GitHub Actions workflow runs `fmt`, `clippy` and every test on Windows and Linux, plus `graphene test --parallel --coverage` and the IDE typecheck, unit tests and headless smoke test (the dev bridge already makes that possible).
- **Releases:** tagged commits build the IDE in **release mode on CI** and attach the installers to a GitHub release. The installers are **unsigned** for now (decision 4), so Windows SmartScreen asks for confirmation on first install. Signing can be added later by storing a certificate as a repository secret, with no other changes.
- **Why:** this fixes the local Smart App Control block for real, instead of shipping debug builds.

## 10. Showcase: a multi-item checkout

```
#!graphene 0.3
@intent "Multi-item checkout: price and reserve every line in parallel, charge once, release everything on failure"

extern fx Catalog(sku: str) -> {price: dec, kg: dec} ! UnknownSku
extern fx Reserve(sku: str, qty: u64) -> str ! OutOfStock
extern fx Charge(buyer: u64, amount: dec) -> str ! Declined | GatewayDown
extern fx~ Release(reservation: str)
extern fx~ Notify(buyer: u64, message: str)

graph PriceLine(line: {sku: str, qty: u64} -> L) -> {sku: str, qty: u64, amount: dec, kg: dec} ! UnknownSku {
  L -> fx Catalog(sku: line.sku) -> ITEM | err -> MISSING
  MISSING -> fail
  ITEM -> f({sku: line.sku, qty: line.qty, amount: ITEM.price * dec(line.qty), kg: ITEM.kg * dec(line.qty)}) -> PRICED
  PRICED -> out
}

graph ReserveLine(line: {sku: str, qty: u64, amount: dec, kg: dec} -> L) -> str ! OutOfStock {
  L -> fx Reserve(sku: line.sku, qty: line.qty) -> RES | err -> NONE
  NONE -> fail
  RES -> out
}

graph IsHeavy(line: {sku: str, qty: u64, amount: dec, kg: dec} -> L) -> bool {
  L -> f(line.kg > 20.00) -> HEAVY
  HEAVY -> out
}

in buyer: u64
in cart: [{sku: str, qty: u64}] -> CART

CART -> map PriceLine(line: each cart) -> LINES | err -> BAD_LINE
BAD_LINE -> fail

LINES -> map ReserveLine(line: each LINES) -> HELD | err -> SHORT
SHORT -> fx~ Notify(buyer: buyer, message: "an item in your cart just sold out") -> sink TOLD
SHORT -> fail OutOfStock

HELD -> filter IsHeavy(line: each LINES) -> HEAVY
HEAVY -> f(round(sum(LINES.amount) * 1.20 + 9.50 * dec(len(HEAVY)), 2)) -> TOTAL

TOTAL -> fx Charge(buyer: buyer, amount: TOTAL) -> TX | err Declined -> DECLINED | err -> PAY_DOWN
DECLINED -> fx~ Release(reservation: each HELD) -> sink UNDONE_1
DECLINED -> fail CardDeclined
PAY_DOWN -> fx~ Release(reservation: each HELD) -> sink UNDONE_2
PAY_DOWN -> fail PaymentUnavailable

TX -> fx~ Notify(buyer: buyer, message: "order " + TX + " confirmed") -> sink THANKS
TX -> f({lines: LINES, heavy_items: len(HEAVY), total: TOTAL, transaction: TX}) -> RECEIPT
RECEIPT -> out receipt: {lines: [{sku: str, qty: u64, amount: dec, kg: dec}], heavy_items: u64, total: dec(2), transaction: str}

assert total
assert indep(TOLD, out)
assert indep(UNDONE_1, out)
assert indep(UNDONE_2, out)
assert indep(THANKS, out)
```

What this shows:
- **Lines in parallel:** every line is priced and reserved in parallel.
- **Undo on payment failure:** a failed payment releases every reservation with one `fx~ Release(reservation: each HELD)` (§8.1).
- **Lists:** projection (`LINES.amount`), the aggregates `sum` and `len`, and `filter`.
- **Strings and scale:** string `+` builds the confirmation message, and `dec(2)` gives an explicit output scale.
- **Proven before running:** the checker still proves that every run ends in exactly one outcome, and that no notification can affect the receipt.

One more limit this exposes: an `OutOfStock` in line 3 doesn't release lines 1–2 that were reserved. Each element's failure is independent, and a map can't see its siblings. The pattern is to reserve with a subgraph that returns `ok: bool` instead of failing, then `filter` and release. That is shown in `examples/valid/cart_checkout.grph` once implemented. Atomic "all or nothing" maps are listed under §12.

## 12. Deferred to v0.4 or later

- **All-or-nothing maps** (`map!`), where any element's failure skips the remaining elements' effects. This needs transactional hosts.
- **Retries and timeouts as syntax** (`fx Charge(...) retry 3 on GatewayDown`). Hosts handle timeouts in v0.3.
- **Multi-file programs** (`import "lines.grph"`). Subgraphs are per file in v0.3.
- **Generic subgraphs** (`graph Sum<T>`), and **folds** beyond the built-in aggregates.
- **String formatting** of numbers, and **indexing** lists.
- An **LSP** server for other editors, reusing `graphene-ide-core`.

## 13. Decisions

1. **Map failure policy: every element runs, and the lowest-index error wins.** It is deterministic and matches D-015. (Fail-fast was rejected.)
2. **Real hosts ship in v0.3** (§6).
3. **List inputs are allowed** (§2), which relaxes D-014 for lists only.
4. **No code signing for now.** There is no budget for a certificate. CI builds optimized but unsigned installers, so SmartScreen warns on first install. Signing can be switched on later without other changes (§8.6).
