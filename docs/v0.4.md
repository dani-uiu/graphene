# Graphene v0.4 — proposal

Status: **approved** (decisions in §11). Not implemented yet.

After approval, these rules move into `grammar.ebnf`, `semantics.md` (§9) and `decisions.md` (D-059 onward).

## Goal

Writing the v0.3 flagships (`payroll_run.grph`, `invoice_split.grph`) hit four walls:

1. **Types are repeated.** `payroll_run` spells out `{id: u64, name: str, gross: dec, tax: dec, net: dec, overtime: bool, remote: bool}` six times. Changing one field means editing six places, and a mismatch is a confusing G003.
2. **Fixed sets of values are plain strings.** Approvers (`"cfo"`, `"ceo"`), regions (`"es"`, `"remote-eu"`) and statuses are `str`, so a typo like `"remote_eu"` compiles and quietly takes the wrong branch. `match` can't check that every case is handled.
3. **No reuse across files.** `LineTotal` is written twice, in `cart_checkout` and `invoice_split`, because subgraphs are per file.
4. **No dates.** "Late" had to be a `bool` input. Real billing needs due dates and "days late".

v0.4 removes all four, and fixes the rough edges found along the way. As before, every 0.1, 0.2 and 0.3 program stays valid and behaves the same.

| # | Change | Kind |
|---|---|---|
| 1 | **Type aliases**: `type Slip = {...}` | language |
| 2 | **Enums**: `enum Region { Spain, RemoteEu, RemoteUs }`, checked by `match` | language |
| 3 | **Imports**: `import "lib/billing.grph"` shares types, enums, constants, effects and subgraphs | language, tooling |
| 4 | **Dates**: a `date` type with `days_between`, `add_days`, and comparisons | language |
| 5 | **Smaller fixes**: keywords as field names, `min(a, b)` / `max(a, b)`, a formatter that wraps long declarations and expressions | language, tooling |
| 6 | **IDE**: multi-file projects, enum and date inputs, extract-into-subgraph | tooling |

## 0. Versioning

`#!graphene 0.4` is added. Every construct below is P006 under an older header: "`<feature>` requires `#!graphene 0.4`". The new words `type`, `enum`, `import` and `date` are contextual, like `graph` and `each`, so older programs that use them as names still work (D-036).

The exception is §5.1 (keywords as field names). It only accepts programs that used to be errors, so it applies to every version, like the v0.3.1 additions (D-055).

## 1. Type aliases

```
type Employee = {id: u64, name: str, hours: u64, rate: dec, region: Region}
type Slip = {id: u64, name: str, gross: dec, tax: dec, net: dec, overtime: bool, remote: bool}

graph NetPay(e: Employee -> E) -> Slip ! UnknownRegion | TableDown { ... }
in staff: [Employee] -> STAFF
REPORT -> out report: {paid: u64, slips: [Slip]}
```

- **Where:** top level only (not inside a `graph` body). An alias can be used anywhere a type can: inputs, parameters, results, `out`, target annotations, constants, `extern` signatures, and inside other types (`[Slip]`).
- **Structural:** an alias is just a name for its definition. `Slip` and the record it names are the same type, so existing code that writes the record out keeps working.
- **Names:** aliases share one namespace with enums. By convention they are `CamelCase`. Redefining a built-in type name (`str`, `date`, …) or another type is G013.
- **No cycles:** `type A = {b: B}` with `type B = {a: A}` is the new **G019**. Records are finite.
- **Unused:** an alias that is never used is G008, like unused constants.
- **Messages:** diagnostics print the alias name when the type came from one (`expected Slip, found {id: u64, ...}`), with the differing field.

## 2. Enums

```
enum Region { Spain, RemoteEu, RemoteUs }
enum Approver { Cfo, Ceo, Intern }

in region: Region -> R
R -> match region { Spain => ES, RemoteEu => EU, RemoteUs => US }
ES -> f(if approver == Approver.Cfo then 0.20 else 0.21) -> RATE
```

- **Values:** a variant is written `Region.Spain` in expressions. In `match` arms the bare variant (`Spain`) is enough, because the scrutinee's type is known. An unknown variant is G002, with "did you mean `RemoteEu`?".
- **Nominal:** two enums with the same variants are still different types. Enums never mix with `str` or numbers: `region == "Spain"` is G003.
- **Operations:** `==` and `!=`, `match` (with exhaustiveness), `contains` on `[Region]`, and `str(region)`, which gives `"Spain"`. Ordering (`<`) is G003, because declaration order is not meaningful.
- **Exhaustiveness (G004):** a match on an enum is total when it lists every variant, or has `_`. Adding a variant later makes every `match` without `_` fail to check. That's the point: the compiler lists the places to update.
- **JSON:** a variant is its name as a string, `"Spain"`. Inputs and mock answers are checked against the enum: an unknown name in an input is R005, and in a host answer it's R004.
- **No data in variants** in v0.4. `Pending(since: date)` needs optional values and payloads, deferred to v0.5 (§10).
- **Errors stay separate.** Effect and subgraph errors (`! NotFound | DbDown`) keep their own syntax and rules.

## 3. Imports

```
#!graphene 0.4
import "lib/billing.grph"

in lines: [Line] -> L
L -> map LineTotal(line: each lines) -> AMOUNTS
```

- **Libraries:** an imported file has a `#!graphene 0.4` header and contains only declarations: `type`, `enum`, `const`, `extern`, `graph`, and its own `import`s. A file with inputs, flows, `out` or `assert` is a program, not a library. Importing one is **G018**.
- **Paths** are relative to the importing file and end in `.grph`. There are no search paths, environment variables or URLs, so a program means the same thing on every machine.
- **Flat names:** everything a library declares becomes visible as if written in the importing file. A name defined in two places is G013, and the message names both files. Reaching the same file through two paths is fine; files are identified by their resolved path.
- **Problems are G018:** file not found, not a library, an import cycle (`a` imports `b` imports `a`), or `check` called on text with no file path.
- **Unused** imports are G008.
- **Checking:** each library is checked once, on its own, then its declarations are added to the importer. A diagnostic inside a library is reported against that file, with its own line numbers.
- **Running:** imports are resolved at check time. The runtime, the effect log and `.cases.json` files don't change.
- **API:** `graphene::check(src)` stays for single files. A new `check_file(path)` resolves imports from disk. The CLI and the IDE use `check_file`.

## 4. Dates

```
in due: date
in today: date
in amount: dec -> A
A -> f(days_between(due, today)) -> LATE              // i64, negative when early
LATE -> match LATE > 30 { true => OVERDUE, false => FINE }
OVERDUE -> f({amount: amount, remind_on: add_days(today, 7)}) -> NOTICE
```

- **`date`** is a calendar date: no time of day, no time zone. Years run from 1 to 9999.
- **Literals:** `date("2026-11-02")`. The argument must be a literal in `YYYY-MM-DD` form, checked at compile time (G003).
- **JSON:** `"2026-11-02"`. A bad date in an input is R005; in a host answer, R004.
- **Operations:**

| Expression | Typing | Value |
|---|---|---|
| `a == b`, `a < b`, … | two `date` give `bool` | calendar order |
| `days_between(a, b)` | two `date` give `i64` | `b - a` in days |
| `add_days(d, n)` | `date`, `i64` give `date` | out of range is R001 |
| `year(d)`, `month(d)`, `day(d)` | `date` gives `u64` | the parts |
| `weekday(d)` | `date` gives `u64` | 1 = Monday … 7 = Sunday |
| `str(d)` | gives `str` | `"2026-11-02"` |

- **No "now".** Reading the clock would make runs non-deterministic, so today's date is always an input. Tests can then pin it.

## 5. Smaller fixes

### 5.1 Keywords as field names

Today a record field can't be called `f`, `in`, `out`, `match`, … (P001). After `.` and before `:` inside a record, every keyword is now accepted as a field name: `{f: 1, out: 2}`, `x.in`. This applies to every version, because it only accepts programs that were errors before.

### 5.2 `min` and `max` of two values

`min(a, b)` and `max(a, b)` take two values of the same numeric, `str` or `date` type. Today you have to write `min([a, b])`. The one-list forms stay.

### 5.3 The formatter wraps more

Today only records, argument lists and `graph` headers wrap at 100 columns, so `extern` lines and long expressions can run past 140 characters. v0.4 also wraps:
- `extern` signatures, one parameter per line;
- the outermost function call, list or record inside a long expression, one argument per line.

This changes the canonical form of some existing 0.3 files, so the examples are re-formatted once. Round-trip and determinism tests must still pass byte for byte.

## 6. IDE

- **Multi-file projects:**
  - imports resolve against the open folder;
  - "Go to definition" opens the library;
  - imported subgraphs appear as groups marked with their file, read-only in that program;
  - saving a library re-checks the programs open in other tabs.
- **Run form:**
  - enum inputs become a dropdown of their variants;
  - date inputs get a date picker;
  - lists of records with enum or date fields are still typed as JSON.
- **Extract into subgraph** (deferred since v0.3): select statements, then *Extract into subgraph…*. The selection becomes a `graph` block plus a `call`. It works when the selection has exactly one flow in and one flow out; otherwise the IDE says which flow is in the way.
- **Highlighting and autocomplete** for `type`, `enum`, `import`, `date`, variants and the date functions.
- Installers stay Windows-only in v0.4 (§11).

## 7. New and changed diagnostics

| Code | Change |
|---|---|
| **G018** | new: an import can't be used (file not found, not a library, import cycle, no file path) |
| **G019** | new: a type alias refers to itself, directly or through other aliases |
| G002 | also unknown types, enums and variants, with "did you mean" |
| G003 | also enums compared with other types or ordered; invalid date literals |
| G004 | also enum matches that miss a variant (the help lists the missing ones) |
| G008 | also unused types, enums and imports |
| G013 | also names clashing across files (both files named) |
| P006 | also v0.4 syntax under older headers |
| R004 / R005 | also unknown enum variants and invalid dates, from hosts / inputs |
| R001 | also dates out of range |

## 8. Showcase: payroll, split into a library

The flagship is rewritten as a library plus a short program. This is a sketch; phase A writes and checks the real files.

`examples/valid/lib/payroll.grph`:
```
#!graphene 0.4

enum Region { Spain, RemoteEu, RemoteUs }
enum Approver { Cfo, Ceo, Intern }
type Employee = {id: u64, name: str, hours: u64, rate: dec, region: Region}
type Slip = {id: u64, name: str, gross: dec, tax: dec, net: dec, overtime: bool, remote: bool}

const STD_HOURS: u64 = 160
extern fx TaxTable(region: Region) -> {rate: dec, credit: dec} ! TableDown

graph NetPay(e: Employee -> E) -> Slip ! TableDown { ... }
graph Payable(slip: Slip -> S) -> bool { ... }
```

`examples/valid/payroll_v4.grph`:
```
#!graphene 0.4
import "lib/payroll.grph"

in period: date
in approver: Approver
in staff: [Employee] -> STAFF
...
FUNDED -> match approver { Cfo => APPROVED, Ceo => APPROVED, Intern => UNAPPROVED }
```

Gains:
- each record type is written once;
- `UnknownRegion` disappears, because a region that isn't in the enum can't reach the program (R005 at the input);
- the approval `match` lists every approver, so adding `Cto` later makes the checker point at it.

## 9. Implementation phases

| Phase | Work | Done when |
|---|---|---|
| A | Spec: `grammar.ebnf`, `semantics.md` §9, decisions D-059 onward; examples: payroll as library + program, a dates example (late invoices), one invalid example per new or extended code | You approve |
| B | Front end: `type`, `enum`, `import`, `date(...)`, `Enum.Variant`, bare variant patterns, keyword field names, two-value `min`/`max`, `0.4` header and P006; formatter wrapping; proptest generator extended | Parse and round-trip tests pass; existing examples re-formatted once and byte-stable |
| C | Checker: type table (aliases and enums), G019, enum typing and exhaustiveness, dates; imports: loader, library rules, G018, cross-file G013, diagnostics that carry their file | All examples check; each new invalid example gives exactly its code |
| D | Runtime: enum and date values, input binding, host-answer checks, date functions | Cases pass, sequential and parallel; the 200× determinism test still passes |
| E | CLI: `check` / `run` / `test` / `fmt` / `graph` follow imports; `explain` gets G018 and G019; coverage counts imported subgraphs in each program that uses them | CLI tests cover a multi-file program |
| F | IDE: multi-file analysis, go to definition, enum and date inputs, extract into subgraph, highlighting | Smoke test extended (open a program with imports, run it with an enum input, extract a subgraph) and green |
| G | Release: README, usage guide, `learn.html` lessons for types, enums, imports and dates; versions `graphene` 0.4.0 and IDE 0.3.0; tag | CI green; a tag produces the Windows installers |

Each phase ends with fmt, clippy and the tests clean, a commit, and a 5-line report.

**Main risk:** diagnostics today point into one source text. Imports need a file attached to every diagnostic, which touches rendering in the CLI, the IDE's Problems panel and the JSON output. That change happens first in phase C, on its own commit.

## 10. Deferred to v0.5 or later

- **Optional values and variants with data** (`Pending(since: date)`), and **errors that carry data** (`fail Short(missing: 3)`). These need one shared design.
- **Generic subgraphs** (`graph Sum<T>`) and **folds** beyond the built-in aggregates.
- **Retries as syntax** (`fx Charge(...) retry 3 on GatewayDown`).
- **All-or-nothing maps** (`map!`), which need transactional hosts.
- **Time of day and time zones**.
- An **LSP** server for other editors, reusing `graphene-ide-core`.
- **macOS and Linux installers** (not yet; CI already checks the language on Linux).
- **Code signing** for the installers, once there's a certificate.

## 11. Decisions

1. **Enum values:** `Region.Spain` in expressions, bare `Spain` in match arms (§2).
2. **Imports:** flat names; a clash is G013 naming both files (§3).
3. **Dates ship in v0.4**, calendar dates only (§4).
4. **The new formatter wrapping applies to 0.3 files too.** The examples are re-formatted once (§5.3).
5. **No macOS or Linux installers yet** (§10).
