# Graphene v0.2 — proposal

Status: **implemented.** The rules are in `grammar.ebnf`, `semantics.md` §6 and `decisions.md` (D-029 to D-036). This file remains the design rationale.

After approval, these rules move into `grammar.ebnf`, `semantics.md` and `decisions.md` (as D-029 onward), and this file becomes the v0.2 implementation plan.

## Goal

Fix the limits that writing `checkout.grph` exposed, and add two tools for the LLM write → check → fix loop. Every v0.1 program stays valid and behaves the same.

| # | Change | Kind |
|---|---|---|
| 1 | Input names usable everywhere, and input nodes optional | language: scope rule |
| 2 | Record literals in expressions | language: new expression |
| 3 | Error edges per variant | language: new edge syntax |
| 4 | Numeric conversions `u64()`, `i64()`, `dec()` | language: new expression |
| 5 | `graphene test` | tooling |
| 6 | `graphene check --json` | tooling |

---

## 0. Versioning

- The header may be `#!graphene 0.1` or `#!graphene 0.2`. Anything else is still **P003**.
- **A `0.1` file is checked and run exactly as in v0.1.** Using a v0.2 feature in it is a new error, **P006** "`<feature>` requires `#!graphene 0.2`", with the help line "change the header to `#!graphene 0.2`; v0.2 accepts every v0.1 program".
- v0.2 is a strict superset: changing a valid 0.1 file's header to 0.2 never changes its meaning.
- `graphene fmt` keeps the header version as written.
- All examples move to `0.2` except two kept on `0.1` as regression tests: `pricing.grph`, which the brief requires verbatim, and one invalid example that only fails under 0.1.

## 1. Inputs usable everywhere

**Problem.** An expression may only reference a value whose node dominates it. An input name counts as its input node, so on a conditional branch you can't use `sku` or `qty` unless every path passes through that input's node. In practice that's never true, so v0.1 programs had to fetch everything through one record.

**Rule.** An **input name** may be referenced in any expression, anywhere in the program. Inputs are bound before the run starts and never become inactive, so the reference is always safe in both sequential and parallel execution.

- The dominance rule (G009) still applies to **value nodes**. `scope_violation.grph` stays an error.
- Using the **input node** (`A`) in an expression is still G002.

**Optional input node.** If an input is only used in expressions, it doesn't need a node:

```
in usr_id: u64          // a parameter: no node, no flow starts here
in sku: str -> K        // as in v0.1: K is a flow source
```

- An input without a node creates no graph vertex.
- It must be referenced at least once. An unused input is **G008** ("input `x` is never used"), the same code as an input node with no flow.

**Considered, not chosen:** allowing a reference to any value that is guaranteed to have run (when the referencing step runs, the value must already be computed). It's more general, but harder to explain in an error message. Inputs cover the cases we've hit. This can be revisited.

## 2. Record literals

**Problem.** A computation or join can only produce one scalar, so a result can't carry several numbers.

**Syntax.** A new expression atom:

```
record_lit = "{" , field_init , { "," , field_init } , [ "," ] , "}" ;
field_init = IDENT , ":" , expr ;
```

```
(RATE, SHIP) -> f({subtotal: SUB, shipping: SHIP, total: SUB + SHIP}) -> BILL
BILL -> out bill: {subtotal: dec, shipping: dec, total: dec}
```

- **Type:** a record with those fields. Field names must be unique (G013). An empty `{}` is P001.
- Fields can be read back with `.`, including directly on the literal (`{a: 1}.a`).
- Records still can't be compared with `==` or used as a `match` scrutinee (G003).
- **Integer literals** inside a field follow the v0.1 rules: `u64` unless context says otherwise. A target annotation (`-> T: {n: i64}`) supplies that context. This is a new rule: annotations now guide literal typing instead of only being checked against it.
- **No ambiguity with `match`.** A scrutinee is a complete expression, so the `{` that follows it always starts the arm list. A record scrutinee is a type error anyway.
- **Output:** `dec` fields at any depth are rescaled to 2 places, as in v0.1 (D-002).

## 3. Error edges per variant

**Problem.** `| err ->` sends every error to one place. In `checkout`, a database outage (`DbDown`) quietly got guest pricing, the same as `NotFound`.

**Syntax.** An `fx` statement may have several error edges. Each one is named or catch-all:

```
err_edges = { "|" , "err" , [ IDENT ] , "->" , IDENT } ;
```

```
A -> fx DbFetch(table: "usr", key: id) -> USR | err NotFound -> GUEST | err DbDown -> DOWN
A -> fx DbFetch(table: "usr", key: id) -> USR | err DbDown -> DOWN | err -> OTHER
A -> fx DbFetch(table: "usr", key: id) -> USR | err -> E          // v0.1 form, unchanged
```

**Rules.** For an effect declared with errors `V1 | … | Vn`:

- **Coverage (G005).** Every declared variant goes to exactly one edge: its own named edge, or the catch-all if one is present. A variant with no edge is G005, with the help line "add `| err Vk -> …` or a catch-all `| err -> …`". The message lists the missing variants.
- **Unknown variant (G002).** `| err Typo -> …` names an error the effect doesn't declare.
- **Redundancy (G014).**
  - A variant named twice is redundant.
  - A catch-all is redundant when every variant already has its own edge.
  - A catch-all must come last.
- **Value:** the error node holds the variant, as in v0.1. A bare `fail` from it returns that variant, for example `Err DbDown`.
- **Merging:** two error edges of the same effect may target the same node. They are exclusive, so the merge check accepts it.

**Guards.** A sync effect with errors becomes a decision with outcomes `ok, V1, …, Vn`, just like a `match` with n+1 arms. A named edge is active on its variant. The catch-all is active on the variants not named elsewhere. The existing normalization, which collapses sibling outcomes, makes the v0.1 single `| err ->` behave exactly as before. The `ok(x)` / `err(x)` atoms are re-expressed as outcomes of this decision, so no v0.1 guard changes meaning.

## 4. Numeric conversions

**Problem.** `u64`, `i64` and `dec` never mix and there was no way to convert, so `price * qty` was impossible when `qty: u64`.

**Syntax.** A new expression atom:

```
conversion = ( "u64" | "i64" | "dec" ) , "(" , expr , ")" ;
```

The type names stay ordinary identifiers. `IDENT "("` never appears in a v0.1 expression, so there's no ambiguity, and fields or nodes named `dec` remain legal.

| From → To | Result | Fault |
|---|---|---|
| `u64` → `i64` | same value | R001 if above `i64::MAX` |
| `i64` → `u64` | same value | R001 if negative |
| `u64`/`i64` → `dec` | exact | none (fits in `dec`'s range) |
| `dec` → `u64`/`i64` | **truncates toward zero**, like integer `/` | R001 if out of range, or negative for `u64` |
| same type → same type | no-op | none |
| `bool`, `str`, records | G003 | |

Conversions stay explicit. v0.1's "no implicit conversions" rule (D-014) is unchanged.

## 5. `graphene test`

Runs `.cases.json` files and reports pass or fail. The files already exist.

```
graphene test                        # every examples/**/X.cases.json next to an X.grph, from the current folder down
graphene test examples/valid/checkout.grph
graphene test --parallel             # run each case sequentially and in parallel; both must match
```

- **A case passes** when the JSON that `graphene run` would print equals `expect` exactly. That covers both the `{result, effects}` and the `{fault, effects}` shapes, so expected faults can be tested too. Key order doesn't matter.
- **Mock paths** are resolved relative to the `.cases.json` file. The existing files change from `"fixtures/users.json"` to `"../../fixtures/users.json"`, and the Rust test harness is updated to match. This changes path resolution only. No expected result changes.
- **Output:** one line per case (`PASS checkout: premium member…`). A failing case also prints the first differing JSON path, with its expected and actual values. A summary line comes last.
- **Exit codes:** 0 if all cases pass, 1 if any case fails or a program doesn't check.

## 6. `graphene check --json`

The same diagnostics as data, for tools and LLM fix loops:

```json
[
  {
    "code": "G005",
    "message": "`fx DbFetch` can fail but the error is not handled",
    "file": "examples/invalid/unhandled_err.grph",
    "span": { "start": 120, "end": 167, "line": 8, "col": 1, "end_line": 8, "end_col": 48 },
    "labels": [ { "span": { "...": "..." }, "text": "may raise NotFound | DbDown" } ],
    "help": "add an error edge: `... -> Target | err -> ErrNode`, then handle `ErrNode` (for example `ErrNode -> fail`)"
  }
]
```

- `start` and `end` are byte offsets. `line` and `col` are 1-based, with `col` counted in characters.
- A valid program prints `[]`.
- Output goes to stdout. Exit codes are unchanged (0 valid, 1 errors).

## 8. Showcase: `checkout.grph` rewritten for v0.2

```
#!graphene 0.2
@intent "Check out an order: verify stock, price it with a member discount and a shipping quote fetched in parallel, hold large orders"

extern fx Catalog(sku: str) -> {price: dec, stock: u64, kg: dec} ! UnknownSku
extern fx DbFetch(table: str, key: u64) -> {role: str, bal: dec} ! NotFound | DbDown
extern fx ShipQuote(zone: str, kg: dec) -> dec ! NoRoute
extern fx~ LogAsync(event: str, role: str)
extern fx~ Audit(event: str, sku: str)

in sku: str -> K
in usr_id: u64
in qty: u64
in zone: str

K -> fx Catalog(sku: sku) -> ITEM | err -> NO_ITEM
NO_ITEM -> fail

ITEM -> match ITEM.stock >= qty { true => STOCKED, false => SHORT }
SHORT -> fx~ Audit(event: "short", sku: sku) -> sink AUDIT
SHORT -> fail OutOfStock

// Unknown customers pay as guests; a database outage is now its own failure.
STOCKED -> fx DbFetch(table: "usr", key: usr_id) -> USR | err NotFound -> GUEST | err DbDown -> DOWN
DOWN -> fail
USR -> match USR.role { "prem" => PREM, "staff" => STAFF, _ => BASIC }
USR -> fx~ LogAsync(event: "checkout", role: USR.role) -> sink LOG
PREM -> f(0.80) -> RATE
STAFF -> f(0.70) -> RATE
BASIC -> f(1.00) -> RATE
GUEST -> f(1.00) -> RATE

RATE -> fx ShipQuote(zone: zone, kg: ITEM.kg * dec(qty)) -> SHIP | err -> NO_ROUTE
NO_ROUTE -> f(25.00 + ITEM.kg * dec(qty) * 5.00) -> SHIP

SHIP -> f({subtotal: ITEM.price * dec(qty) * RATE, shipping: SHIP, total: ITEM.price * dec(qty) * RATE + SHIP}) -> BILL

BILL -> match BILL.total > 1000.00 { true => BIG, false => SMALL }
BIG -> fail NeedsApproval
SMALL -> out bill: {subtotal: dec, shipping: dec, total: dec}

assert total
assert indep(LOG, out)
assert indep(AUDIT, out)
```

This version uses all four language changes:
- **Plain inputs:** `usr_id`, `qty` and `zone` have no node, and `qty` is read deep inside branches.
- **Conversions:** `dec(qty)`.
- **Per-variant errors:** a database outage (`DbDown`) is now its own failure.
- **A record result:** the bill carries its subtotal, shipping and total.

It's about the same length as the v0.1 version but does more. The v0.1 `checkout.grph` is kept as is, as a 0.1 regression example.

**One trade-off.** In v0.1, the customer lookup and the shipping quote ran in parallel and were then joined. That no longer works here. `DbDown` now fails on its own path, so `RATE` isn't guaranteed whenever `SHIP` is, and joining them would be G007. The shipping quote now runs after the discount instead. `SHIP` still reads `RATE` without a join, because every path to `SHIP` passes through `RATE`.

This will be common: once one branch can fail, it can no longer be joined with a branch that can't. §11 lists a possible relaxation.

## 11. Deferred to v0.3 or later

- Lists, and mapping over them (multi-item orders). This is the biggest open design question.
- `dec(N)` output scale per `out` instead of always 2 places.
- Rounding functions (`round(x, 2)`).
- Real effect hosts (HTTP, subprocess).
- Allowing a reference to any value guaranteed to have run (§1, "considered").
- **Relaxing G007.** Allow a join when one member's active condition implies all the others', so the join is active exactly when the most specific member is. This would bring back the parallel lookup in §8. It changes a rule from the brief, so it needs its own decision.
